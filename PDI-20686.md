## 1. Executive summary

**The ask.** In PDI **10.2.0.1** the Data Explorer Tool (DET) EE was built into the product and worked.
From **10.2.0.2** onward DET ships as a separate **KAR** add-on, and in 10.2.0.X that KAR could only be
*hot* deployed (dropped into a running PDI), and even then the **Model view was empty** and several
visualizations did not work. PDI-20686 asks for a DET EE KAR that also works on a **cold start** (the
KAR already present in `deploy/` when PDI is launched with an empty cache), with a fully functional
Model view.

**Why it broke.** Nothing about DET changed. Between 10.2.0.1 and 10.2.0.X, a series of **mandatory
security and platform upgrades** removed, one by one, every piece of plumbing DET silently relied on:
Spring DM (which carried 13 Spring 3.2.18 CVEs), the four Analyzer content-generator beans, the
common-ui plugin, and the legacy Pax Web servlet registration style. Each removal was correct in
isolation; together they left DET without a runtime.

**The fix.** Restore the *contract*, not the vulnerable components:

1. A **~160-line `SpringContextFactory`** in the existing `pentaho-pdi-platform` bundle reproduces the
   one thing Spring DM did for Pentaho plugins — build an `ApplicationContext` from
   `META-INF/spring/*.xml`. Each plugin asks for its own context from its own Blueprint, so there is
   **no new bundle and no OSGi service handshake**. It uses the platform's own **Spring 5.3.39**, so
   **no CVE-bearing Spring is reintroduced**.
2. Restore the **four Analyzer content-generator beans** deleted in SP-6671 (delivered by the PDI
   assembly, not the KAR — see [§6.1](#61-why-the-analyzer-fix-must-ship-in-the-pdi-assembly)).
3. Update servlet registration to the **OSGi R7 HTTP Whiteboard** properties Pax Web 8 requires.
4. Ship **common-ui**, the Analyzer plugin and their runtime dependencies **inside the KAR**, and make
   the KAR resolve in a **single Karaf batch** so it cannot starve PDI's boot features.

**The result.** ✅ Verified on `pdi-ee-client-10.2.0.0-20260818.001718-1758-osgi`:
PDI cold-starts in ~40 s with **no unexpected errors** in `SpoonDebug.txt` (see
[§10.1](#101-expected-log-noise--none-of-these-are-regressions)), all boot features `Started`,
181 bundles `Active`, `bundle:diag` empty, the full 180 KB RequireJS configuration served, the
`/content/analyzer/*` and `/content/geo*` endpoints answering, and the **DET Model view, charts, geo
map and pivot table all working**.

> **This document describes the final, simplified change set.** An earlier iteration introduced two new
> Maven modules (a standalone Spring extender and a no-op `ILineageClient` stub); both were removed
> after review — see [`PDI-20686-errata.md`](./PDI-20686-errata.md). The delivery now introduces **no
> new modules and no new OSGi bundles**, only edits to existing ones.

> **Hot deploy.** This change set is scoped to the cold start, but most of it is a prerequisite for hot
> deploy too, and hot deploy has been manually exercised on the test install and behaves correctly.
> The items marked 🔥 in [§5](#5-change-footprint-per-repository) are the ones that help both. The
> Spoon-side work that makes a hot deploy fully indistinguishable from a cold start is a **follow-up**,
> documented in [`PDI-20686_hot.md`](./PDI-20686_hot.md).

## 4. The solution in one picture

```
              PDI 10.2.0.10 assembly                       pentaho-det-ee-pdi KAR
              ─────────────────────                        ──────────────────────
 karaf/system/pentaho/paz-plugin-ce/…zip            karaf/deploy/pentaho-det-ee-pdi-….kar
   ├─ plugin.spring.xml    ← 4 CG beans restored      ├─ feature: pdi-platform
   └─ analyzer_beans.xml   ← builds its own           ├─ feature: pentaho-requirejs-osgi-manager
                             Spring context           ├─ feature: pentaho-deployers
                                                      ├─ feature: pentaho-i18n
 karaf/system/pentaho/pentaho-pdi-platform/…jar       ├─ feature: pax-web-jsp
   └─ SpringContextFactory  ◄── NEW CLASS             ├─ bundle:  paz-plugin-ce (zip)
                                                      ├─ bundle:  icu4j
 karaf/etc/custom.properties                          ├─ bundle:  common-ui (zip)
   └─ exports Spring 5.3.39 as system packages        └─ …DET, CDE/CPF, geo, viz bundles
```

**Cold-start sequence** (✅ verified in `SpoonDebug.txt` + Karaf shell):

```
 1. Karaf boots ──► boot features install (ssh, pentaho-client-minimal, pentaho-big-data-plugin-osgi)
 2. KAR deployer picks up pentaho-det-ee-pdi-….kar
 3. The whole KAR feature graph resolves in ONE batch  (no prerequisite="true" anywhere)
 4. pentaho-platform-plugin-deployer converts paz-plugin-ce.zip and common-ui.zip into bundles;
    SpringFileHandler reads plugin.spring.xml and emits, per <bean id="…">, a Blueprint
      <service interface="javax.servlet.Servlet">
        osgi.http.whiteboard.servlet.pattern = /content/analyzer/<name>/*
        osgi.http.whiteboard.servlet.name    = <bean id>
      referencing the ApplicationContext of the analyzer bundle
 5. The analyzer's own analyzer_beans.xml declares
      <bean id="spring" class="org.pentaho.platform.pdi.SpringContextFactory"
            factory-method="createForBundle" destroy-method="close">
        <argument ref="blueprintBundle"/>
      </bean>
    so Blueprint builds the Spring context from META-INF/spring/*.xml as an ordinary local bean
 6. The generated servlet definitions reference that same "spring" bean id, so Blueprint cannot
    publish them until the context exists ──► the four ContentGeneratorServlets register with Pax Web 8
    (pentaho-geo-agile-bi does exactly the same for /content/geo*)
 7. DET's own Blueprints build
 8. Spoon opens; DET Model view calls /content/analyzer/* and gets real data
```

Step **6** is the ordering guarantee: the servlets and the context are components of the *same*
Blueprint container, so Blueprint's own dependency ordering guarantees the context is built first. No
sleeps, no retries, no cross-bundle service timeout.

## 6. Design decisions, and why the alternatives were rejected

### 6.1 Why the Analyzer fix must ship in the PDI assembly

📄 **Karaf resolves `mvn:` URLs from `system/karaf/system` before a KAR's embedded `repository/`.**
PDI already ships `mvn:pentaho/paz-plugin-ce/10.2.0.0-SNAPSHOT/zip`, so a *patched* copy placed inside
the KAR is **silently ignored**.

✅ **Verified:** an early cold-start test deployed a KAR containing the patched `plugin.spring.xml`, yet
the bundle Karaf actually installed contained the *stock* file, and `/content/analyzer/*` returned 404.

**Consequence:** the four-bean restoration is a **`pentaho-analyzer` 10.2.0.10 deliverable**, not a KAR
deliverable. In the test environment this is simulated by overwriting the shipped zip
([§9](#9-deploy) step 2).

### 6.2 The Spring context factory

**What it is.** `org.pentaho.platform.pdi.SpringContextFactory` — ~160 lines added to the **existing**
`pentaho-pdi-platform` bundle, alongside the `CompositeClassLoader` it uses. No new module, no new
bundle, no new feature.

**How a plugin uses it.** The plugin's own Blueprint builds its own context:

```xml
<!-- analyzer/OSGI-INF/blueprint/analyzer_beans.xml, shipped inside paz-plugin-ce -->
<bean id="spring" class="org.pentaho.platform.pdi.SpringContextFactory"
      factory-method="createForBundle" destroy-method="close">
  <argument ref="blueprintBundle"/>
</bean>
```

`blueprintBundle` is a component Aries Blueprint predefines for every container, so the factory receives
the plugin bundle itself and builds a `ClassPathXmlApplicationContext` from its
`META-INF/spring/*.xml`.

**Why this shape.** The servlet definitions that `SpringFileHandler` generates already reference
`ref="spring"`. Under Spring DM that id was an *imported OSGi service*; it is now a *local bean*. The
generated servlets are unchanged, but the wiring is strictly better:

| | Spring DM / extender | `SpringContextFactory` |
|---|---|---|
| Ordering guarantee | mandatory OSGi service reference with a **5 s timeout** | Blueprint's own bean dependency ordering — **no timeout, no race** |
| Lifecycle | context outlives the plugin; the extender must dispose it | created and closed **with** the plugin's container (`destroy-method="close"`) |
| Scope | *every* bundle with `META-INF/spring/*.xml` gets a context | only the plugins that ask for one |
| New artifacts | 1 bundle + 1 module | **none** |

**Two pieces of legacy behaviour are reproduced**, so unmodified plugin Spring XML keeps working:

1. **A composite class loader** — plugin bundle first, Spring's class loader second, with
   `getResources()` **merged** across both. Spring discovers XML namespace handlers by enumerating
   *all* `META-INF/spring.handlers` and `spring.schemas`; without merging, `<util:properties>` and
   `<context:annotation-config>` in stock plugin XML fail to parse.
2. **The `plugin:` resource protocol** — via `addProtocolResolver(...)`, so
   `value="plugin:analyzer.properties"` resolves to the matching bundle entry.

⚠️ **Why a `ProtocolResolver` and not a context subclass.** Spring DM's
`PentahoOsgiBundleXmlApplicationContext` subclassed the context to override `getResource()`. Doing that
here throws a `LinkageError` (loader constraint violation), because the bundle's view of
`org.springframework.core.io.Resource` and the superclass' view come from different class loaders. A
`ProtocolResolver` is loaded through the context's own class loader, so it is loader-constraint safe.
✅ Verified — the subclass approach was tried first and failed exactly this way.

⚠️ **Why Spring is not bundled.** ✅ Verified: adding the ServiceMix Spring 5.3.34 wraps creates a second
Spring provider; package wirings split across the two copies and produce a `java.lang.LinkageError`. At
runtime the factory binds to the Spring 5.3.39 that PDI exports through
`system/karaf/etc/custom.properties`.

**Scope — exactly two plugins.** ✅ Verified by scanning the built KAR: only `paz-plugin-ce` (analyzer)
and `pentaho-geo-agile-bi` carry `META-INF/spring/*.xml`. Both were updated. `common-ui` ships no Spring
XML and needs no context.

> ⚠️ **This was found the hard way.** The first build of this design updated only the analyzer, and
> `/content/geojson` began returning **HTTP 500**:
> `ServiceUnavailableException: No matching service for optional OSGi service reference:
> (&(Bundle-SymbolicName=pentaho-geo-agile-bi)(objectClass=…ApplicationContext))`.
> The previous extender was *generic*, so it had been silently supplying geo's context too. Any future
> platform plugin that ships `META-INF/spring/*.xml` needs the same three-line bean.

### 6.3 `ILineageClient` is already provided — no stub needed

An earlier iteration of this work added a no-op `ILineageClient` bundle, on the premise that
`pdi-dataservice-server-plugin`'s mandatory Blueprint reference had no provider in a PDI client.

📄 **That premise was wrong.** ✅ Verified on a running PDI with **no DET KAR installed at all**:

```
karaf@root()> service:list org.pentaho.metaverse.api.ILineageClient
 Provided by : Bundle 105   →  pentaho-blueprint-activators
```

`pentaho-blueprint-activators` runs `PentahoOSGIActivator`, which bridges objects registered in
`PentahoSystem` — including the real `LineageClient` from the metaverse Kettle plugin — into the OSGi
service registry. The dataservice container builds and publishes `IDataServiceMetaFactory` normally.

✅ Confirmed by removal: with the stub deleted, cold start is clean and DET, the Model view and the geo
map all work. The original symptom ("DET containers never build") was caused by the
`prerequisite="true"` feature starvation described in [§6.4](#64-why-nothing-in-the-kar-may-be-prerequisitetrue),
and was misattributed.

> **Lesson for the trap list:** a service can be published by the `PentahoSystem`→OSGi bridge, not only
> by a Blueprint. Scanning jars for a publishing Blueprint is not sufficient — confirm with
> `service:list <interface>` on a running instance.

### 6.4 Why nothing in the KAR may be `prerequisite="true"`

✅ **Verified experimentally.** A variant of `feature.xml` that used `<feature>pentaho-analyzer</feature>`
(whose sub-features `pentaho-analyzer-prerequisites`, `pdi-platform` and
`pentaho-requirejs-osgi-manager` are declared `prerequisite="true"`) produced:

```
ERROR [KarafLifecycleListener] Error in Feature Watcher
… FeatureWatcherException: Timed out waiting for Karaf features to install:
    ssh,pentaho-client-minimal,pentaho-big-data-plugin-osgi
```

and left all three boot features `Uninstalled` even though the DET features themselves started.
A prerequisite forces Karaf into a **nested provisioning batch**; on a clean-cache cold start that
nested batch discards the pending boot-feature request.

Hence:
* `<feature>pentaho-analyzer</feature>` is replaced by its **bundle list**
  (`paz-plugin-ce` zip, `icu4j 63.1`, `rhino 1.7.13`, `pentaho-connections`) plus a plain
  `<feature>pdi-platform</feature>` — mirroring the 10.2.0.1 analyzer feature minus `spring-dm`;
* `karaf-maven-plugin.prerequisiteFeatures` is **emptied** so `pentaho-cpf-pdi` and
  `pentaho-cde-plugin-pdi` are generated as ordinary feature dependencies.

> ⚠️ **Documentation correction.** `DET_IN_PDI_10.2.0.X_PROPOSED.md` §11.8 claimed
> `prerequisite="true"` is acceptable under a cold-start-only policy. **That is wrong** and is
> superseded by the evidence above.

### 6.5 Why `pax-web-jsp` is declared explicitly

CDE (`pentaho-cde-plugin-pdi`) depends on `commons-jxpath`, which has a **mandatory** import of
`javax.servlet.jsp`. Nothing else activates a JSP-capable feature this early in a cold start. Under
hot deploy the feature happened to be active already, which is why the problem only appeared on cold
start.

### 6.6 The `cxfBus` binding was tried and removed

An earlier iteration bound each `jaxrs:server` to the shared OSGi CXF `Bus`, to avoid a
`No DestinationFactory was found for …` error seen during cold start.

✅ **Removed after testing.** With the binding taken off all five DET endpoints, **3 cold starts + 3
undeploy/redeploy cycles** produced zero `DestinationFactory` errors and 200 on every endpoint. The
original race was observed in a much earlier code state, before the `prerequisite="true"` fix in
[§6.4](#64-why-nothing-in-the-kar-may-be-prerequisitetrue); that change appears to have resolved it.
Removing the binding eliminated `pentaho-det` from the delivery entirely.

### 6.7 Rejected alternative — the "rewired RequireJS" approach

The earlier design (`DET_IN_PDI_10.2.0.X.md`, branch `PPUC-752`) achieved hot *and* cold deploy but
required **rewiring the RequireJS configuration and other plugin configuration** so the KAR could carry
common-ui and friends. Concerns were raised about the maintenance burden and the divergence from how
10.2.0.1 worked.

The approach documented here restores the 10.2.0.1 *mechanism* instead of working around its absence,
so the plugins are consumed **as-is** with no configuration rewiring. The trade-off is that it is
validated for **cold start**; see [§11](#11-residual-risks-and-known-issues).

### 6.8 Plugin resources that are not files

`ResourceFileManager.getResourceFilePath()` turned whatever `IPluginResourceLoader.findResources()`
returned into a `Path` with `Paths.get( URI.create( url ) )`. That holds on the Pentaho Server, where
`PluginResourceLoader` serves an exploded `pentaho-solutions/system/analyzer/` and the URL is a
`file:` URL. In PDI the plugin **is** an OSGi bundle, `AgileBiPluginResourceLoader` returns
`bundle://…/analyzer/filters.json`, and `java.nio` has no provider for that scheme:

```
ERROR [PreQualifiedFilterManager] Error loading filters for the catalog '…/MODEL.xml'
      from file filters.json: Provider "bundle" not installed
```

✅ **Reproduced and fixed.** The message surfaced in the UI as *"Cannot get default options"* every
time a value was dragged into the Pivot table, via
`AjaxBean.getOptions()` → `ReportAdapter.getAllDefaultOptions()` → `getDefaultFilters()`.
`CVBaseAppContext.saveProperties()` (`analyzer.properties`) had the same defect.

The fix keeps the `file:` branch byte-for-byte identical — **the Pentaho Server code path does not
change** — and, for any other scheme, copies the resource **once** to a writable directory and returns
that copy, which is then both readable and writable:

| | |
|---|---|
| Writable root | `-Dpentaho.analyzer.writableResourceDir`, else `${karaf.home}/managed-resources`, else `${java.io.tmpdir}/pentaho-analyzer-${user.name}` |
| Layout | the resource's own path inside the bundle, e.g. `managed-resources/analyzer/filters.json` |
| Why there | it is exactly what `ManagedResourceProvider` / `ManagedResourceHandler` already produce for `pentaho-geo-agile-bi` in the same install — one convention, one place for support to look |

`getResourceAsStream()` / `getResourceAsString()` prefer an already-materialized copy, so a value
written through `getResourceFilePath()` is not silently shadowed by the pristine copy still inside the
bundle. Neither method changes behaviour on the server, where a materialized copy never exists.

The copy is the file of record from then on, which raises three problems the implementation has to
answer:

| Problem | Answer |
|---|---|
| The copy must never be published half written — a reader that catches `filters.json` mid-copy gets a JSON parse error, and `CVBaseAppContext.loadProperties()` does `props.clear()` before loading, so a truncated `analyzer.properties` silently empties the Analyzer properties for the whole JVM | the resource is streamed into a temporary file next to the target and published with a single `Files.move()`. The move is deliberately not `REPLACE_EXISTING` unless the copy is being refreshed, so it is also what keeps a second JVM from overwriting the first one's copy — a lock cannot cover that, and every caller builds its own `ResourceFileManager` anyway (hence the *static* materialization lock) |
| An upgraded or hot redeployed plugin ships new defaults, but a copy keyed only by the resource's path would shadow them forever, with no log line saying why | the copy is refreshed when the resource reports a newer timestamp than it. A copy is always at least as recent as the resource it was taken from, so a product write keeps it; only a genuinely newer bundle replaces it — the same "the new plugin's files win" semantics an upgrade has on the server |
| The materialization path is predictable, and the returned file is both read from and written to (`JSONUtil.toJSONFile`, `new FileWriter( props.toFile(), false )`) — a symbolic link planted there by another local user redirects those writes, and a plain file planted there dictates the plugin's configuration | anything already at the location must be a regular file (checked with `NOFOLLOW_LINKS`) owned by the current user, or it is refused; directories are created `rwx------`; and the `java.io.tmpdir` last resort is per user rather than a single guessable name in a world-writable place |

## 12. Replication protocol for an AI agent

A self-contained recipe to reproduce this analysis from scratch.

### 12.1 Ground rules

1. Treat the 10.2.0.1 install and the `_clean` 10.2.0.X install as **read-only references**.
2. Do all testing in the designated test install ([§7](#7-environment)).
3. Delete `SpoonDebug.txt` and `system/karaf/caches` before **every** run — otherwise you are testing a
   warm start.
4. Never kill processes by name. Resolve PIDs against the **install directory**, which is unambiguous:
   `pgrep -f "<install-dir>"` (plus the `SpoonDebug.sh` and Spoon main-class patterns), then `kill`,
   then **poll until gone**, escalating to `kill -9`. A bare `grep "[d]ata-integration"` matches too
   loosely and was observed to leave live instances behind, silently invalidating later measurements.
5. A cold start must complete within **61 s**; a hot deploy within **51 s**.

### 12.2 Investigation sequence

| Step | Question | How to answer it |
|---|---|---|
| 1 | What does a *working* DET look like? | Unzip `paz-plugin-ce.zip`, `pentaho-pdi-platform.jar` and the `pentaho-analyzer` feature from the **10.2.0.1** install. Note the beans in `plugin.spring.xml`, and the feature's bundle list. |
| 2 | What is missing in 10.2.0.X? | `diff` the 10.2.0.1 and 10.2.0.X `karaf/system` trees and the `pentaho-karaf-features-*` XML files. Expect: `spring-dm` gone, `pentaho-analyzer` feature present but not booted, `common-ui` absent. |
| 3 | Which upstream commits removed them? | `git log --all -S"<removed string>" -- <path>` in `pentaho-karaf-assembly`, `pentaho-osgi-bundles`, `pentaho-analyzer`. Cross-check against SP-6671, SP-6688, PPP-5517 / SP-6858. |
| 4 | Why is the Model view empty? | Trace `/cxf/det/core/data/datasources/<id>/MODEL/` → DET calls `/content/analyzer/*` → served by servlets that `SpringFileHandler` generates **from the beans in `plugin.spring.xml`** → beans deleted in SP-6671. |
| 5 | Why do the restored beans still not produce servlets? | The generated Blueprint references an `ApplicationContext` that only Spring DM used to create. Spring DM is gone → nothing creates it → the container stays in grace period. |
| 6 | Why 404 even when the servlets exist? | Pax Web 8 ignores the legacy `alias` property. Confirm with `bundle:services <id>` (service present) versus `curl` (404). |
| 7 | Why does cold start time out? | `grep "Timed out waiting for Karaf features" SpoonDebug.txt`. Then `feature:list \| grep Uninstalled` — the *boot* features are the casualties. Bisect by toggling `prerequisite`. |

### 12.3 Diagnostic cheat-sheet

```bash
# Ports
grep -E "Karaf Port|OSGI Service Port" SpoonDebug.txt

# Errors during startup
grep -in "error\|exception\|unable to resolve\|missing requirement" SpoonDebug.txt

# HTTP probes - these need no Karaf console and are sufficient on their own
H=http://127.0.0.1:9051
curl -so /dev/null -w '%{http_code} %{size_download}\n' $H/requirejs-manager/js/require-init.js
for p in content/analyzer/service content/analyzer/generatedContent content/geojson \
         cxf/det/core/data/datasources cxf/det/core/persistence/states; do
  curl -so /dev/null -w "%{http_code} $p\n" "$H/$p"
done
```

If a Karaf console *is* available (see [§7](#7-environment)), these add detail that HTTP cannot:

```
bundle:diag                       # containers stuck in grace period / unresolved bundles
feature:list | grep -v Started    # features that failed to install
bundle:list -s | grep -i analyzer # is the plugin bundle ACTIVE?
bundle:services <id>              # did the Servlets get published?
kar:list                          # was the KAR picked up at all?
```

### 12.4 Traps discovered the hard way

| Trap | Symptom | Correct response |
|---|---|---|
| A KAR **cannot** override an artifact already present at the same GAV in `karaf/system` | Patched file silently ignored; endpoints 404 | Ship the patch in the PDI assembly, or overwrite the zip in `karaf/system` for testing |
| `prerequisite="true"` anywhere in the KAR feature graph | Boot features left `Uninstalled`; feature-watcher timeout | Keep the whole graph in one resolution batch |
| Subclassing `ClassPathXmlApplicationContext` | `LinkageError` / loader constraint violation | Use `addProtocolResolver(…)` instead |
| Assuming nothing provides a service because no Blueprint publishes it | A stub is added that was never needed | A service can come from the `PentahoSystem`→OSGi bridge. Confirm with `service:list <interface>` on a **running** instance |
| Giving one plugin its Spring context and forgetting the others | `/content/geojson` → HTTP 500 `ServiceUnavailableException` | Scan the KAR for **all** bundles shipping `META-INF/spring/*.xml` |
| Bundling Spring in the KAR | `LinkageError` from split package wirings | Use the Spring the platform exports via `etc/custom.properties` |
| `SpringFileHandler`'s old bean regex matched XML **comments** | Phantom servlet registered with `id=spring` | Anchor the regex on `<bean ` |
| `feature:list` output is wide and pipes truncate | greps return nothing | Redirect to a file first, then grep the file |
| A `.kar` shows `Uninstalled` in `feature:list` while its bundles are `Active` | Confusing but harmless | Trust `bundle:list` / `bundle:diag` and the HTTP endpoints |

## 13. Glossary

| Term | Meaning |
|---|---|
| **DET** | Data Explorer Tool — the ad-hoc analysis UI embedded in Spoon (right-click a step → *Explore*). |
| **KAR** | KARaf ARchive — a Karaf deployment unit bundling a `features.xml` plus an embedded Maven repository. |
| **Cold start** | The KAR is already in `deploy/` when PDI launches with an empty `caches` directory. |
| **Hot deploy** | The KAR is dropped into `deploy/` while PDI is already running. |
| **Content generator** | Legacy Pentaho platform component that renders content for a URL under `/content/<plugin>/…`. |
| **Spring DM** | Spring Dynamic Modules (Spring OSGi) — the abandoned extender that built plugin Spring contexts. |
| **Blueprint** | The OSGi standard successor to Spring DM; Karaf's Aries implementation drives DET's own wiring. |
| **HTTP Whiteboard** | OSGi R7 mechanism for registering servlets via service properties; mandatory from Pax Web 8. |
| **Prerequisite feature** | A Karaf feature that must be fully installed *before* the referring feature is resolved, forcing a nested provisioning batch. |
| **MODEL view** | The DET panel listing the measures/dimensions of a data source; backed by the Analyzer content generators. |
