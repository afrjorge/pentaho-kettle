The Sqoop job entry runs Sqoop **in-process**. When Sqoop submits its MapReduce job,
`org.apache.hadoop.mapreduce.Job` logs the job progress and the final `Counters: N` block (*File System
Counters*, *Job Counters*, *Map-Reduce Framework*, ...). On stock 10.2 those lines show only on the
terminal and never reach the Kettle log channel (Spoon *Logging* tab, Kitchen `-logfile`, `logs/pdi.log`).

Differences from 11.0 that shape this backport:

| | 11.0 (SP-7670) | 10.2 (SP-7669) |
|---|---|---|
| Sqoop job entry | classic Kettle plugin (`kettle-plugins/sqoop/core`) | **OSGi bundle** in Karaf (`kettle-plugins/sqoop`, `system/karaf/system/pentaho/pentaho-big-data-kettle-plugins-sqoop`) |
| Shim | `hadoop-configurations/apachevanilla/` folder on the plugin classpath | **KAR** in `system/karaf/deploy/`, driver bundle `pentaho-hadoop-driver-V1` |
| Problems present | P1, P2, P3 | **P3 only** |

## 3. How to reproduce (AI compatible)

Non-interactive Kitchen runs. Each run leaves `stdout.txt` (terminal), `kettle.log` (Kettle channel via
`-logfile`), `pdi.log`, `karaf.log` and `exit.txt` in `~/pentaho/tickets/PDI-20034/SP-7669/evidence/<label>/`.

```bash
# ~/pentaho/tickets/PDI-20034/SP-7669/run_kitchen.sh <label>
unset PENTAHO_JAVA_HOME
export JAVA_HOME=$HOME/Library/Java/JavaVirtualMachines/corretto-17.0.14.7.1/Contents/Home
export PENTAHO_DI_JAVA_OPTIONS="-Xms1024m -Xmx2048m -Djdk.net.hosts.file=$HERE/jvm-hosts"
rm -rf "$PDI/system/karaf/caches"; rm -f "$PDI"/logs/*.log            # cold Karaf start, clean logs
cd "$PDI" && ./kitchen.sh -file="$JOB" -level=Basic -logfile="$OUT/kettle.log" > "$OUT/stdout.txt" 2>&1
cp "$PDI"/logs/{pdi,karaf,spoon}.log "$OUT/"
```

Check:

```bash
for f in stdout.txt kettle.log pdi.log; do echo "$f: $(grep -c 'Counters' evidence/<label>/$f)"; done
grep 'result=' evidence/<label>/kettle.log
```

A run takes about 40 s (Karaf cold start plus the MapReduce job). Lines in `stdout.txt` that start with
`HH:mm:ss,SSS LEVEL [Class]` come from PDI's Log4j `PENTAHOCONSOLE` appender. Lines that start with
`yyyy-MM-dd HH:mm:ss.SSS - <entry> -` come from the Kettle channel.

Known noise, present in every run including stock: `ERROR [BlueprintContainerImpl] Unable to start container
for blueprint bundle pentaho-hadoop-driver-V1/3.4.0.apachevanilla ... ClassNotFoundException:
com.pentaho.big.data.ee.secure.impersonation.api.ImpersonationMappingService`. It is unrelated to this
backport, and the job still succeeds.

## 4. Problems

Same analysis as SP-7670 (P1-P3); only **P3** reproduces on 10.2.

### P1 - `commons-cli` 1.2 - not reproducible on 10.2

The Sqoop/Hadoop client code runs inside the OSGi driver bundle `pentaho-hadoop-driver-V1`. That bundle
embeds `commons-cli-1.5.0.jar` on its own `Bundle-ClassPath`, so the plugin's
`lib/commons-cli-1.2.jar` (outside OSGi) is never seen. Stock 10.2.0.11 runs the job (`01-baseline`,
`result=[true]`). The PDI-20034 bump in `assemblies/pmr-libraries/pom.xml` is still applied for parity with
master. On 10.2 it only changes `lib/commons-cli` 1.2 → 1.5.0 inside `pentaho-mapreduce-libraries.zip`. The
Karaf feature `assemblies/features` keeps its own `mvn:commons-cli/commons-cli/1.2` bundle.

### P2 - slf4j 1.7 inside `jetty-runner` - already fixed on 10.2

On 10.2 the shim driver is a bundle (`shims/apachevanilla/driver/pom.xml`, `<packaging>bundle</packaging>`,
no `src/main/assembly/zip.xml`). It already ships the repacked jar through
`<Include-Resource>{maven-resources};${project.build.directory}/extra-resources/jetty-runner-${jetty.version}.jar</Include-Resource>`
(`repack-jetty-runner-jar` excludes `org/slf4j/**`). Verified on the released
`pentaho-hadoop-shims-ee-apachevanilla-driver-10.2.0.11-442.jar` inside the KAR:
`jetty-runner-9.4.57.v20241219.jar` has **0** `org/slf4j` entries. The master shim commit `ac35946a` only
touches `zip.xml`, which does not exist on 10.2, so **pentaho-hadoop-shims `SP-7669` has no change**.

### P3 - The Kettle appender only listens to `org.apache.sqoop` - **reproduced**

`kettle-plugins/sqoop/src/main/java/.../AbstractSqoopJobEntry.java` on 10.2 is the same code as on 11.0 (only
license header and module path differ). `attachLoggingAppenders()` adds the `KettleLogChannelAppender` to
`org.apache.sqoop` only. The `org.apache.hadoop.mapreduce.Job` events go to PDI's Log4j configuration, which
on 10.2 is shared with Karaf (`org.apache.logging.log4j.*` exported in `system/karaf/etc/custom.properties`),
so they reach only the `PENTAHOCONSOLE` appender:

```
21:09:13,121 INFO  [Job] Counters: 33          <- stdout.txt only (01-baseline)
	File System Counters
	...
```

### 7.1 L69 `CURRENT_SQOOP_LOGGER`: the stderr-routing test does not cover cross-thread isolation

[Review comment r4376941279](https://github.com/pentaho/big-data-plugin/pull/3035#discussion_r4376941279):

> The new stderr-routing test attaches both executions on the same JUnit thread and only checks an
> unfiltered capturing appender. It therefore does not verify the execution-local isolation introduced here
> or delivery through the filtered Kettle appenders. Please add a coordinated test with two overlapping worker
> threads, distinct logger contexts, and distinct channel IDs, asserting that each stderr message reaches only
> its owning Kettle channel; also verify that an unrelated thread falls back to the original stream.

**Findings**

| Question | Answer |
|---|---|
| Is the observation right? | **Yes.** `redirectsSystemErrorToTheLoggerOfTheOwningExecution` attaches both entries on the JUnit thread and asserts on a `CapturingAppender` without the `logChannelId` filter. Neither cross-thread isolation (`CURRENT_SQOOP_LOGGER`) nor delivery through `HadoopExecutionLogging`'s filtered `NamedKettleLogChannelAppender` is tested. `HadoopExecutionLoggingTest.routesApplicationIdsToTheOwningLogChannelOnly` covers the threaded filter for direct Log4j events, but not the `System.err` path. |
| Is the behaviour correct anyway? | **Yes, in the context PDI uses. Verified 2026-10-26** with a throwaway test on `SP-7669` @ `2f8c171fcc`, deleted afterwards. Setup: two overlapping worker threads, each with its own `AbstractSqoopJobEntry` and a mock channel (`chan-A` / `chan-B`), and an unrelated thread writing to `System.err` while both are attached. With the **default** `LoggerContext` (loader `null`): `chan-A` got only `from-A`, `chan-B` only `from-B`, and `unrelated` went to the original stream. |
| Would the suggested test (distinct contexts) pass? | **No.** With two parentless `URLClassLoader`s (distinct contexts), neither channel receives anything. The unrelated-thread fallback still works. This is the same root cause as 7.3 / `SP-7670.md` 7.2: `LogUtil.addAppenderWithLevel` (pentaho-platform, PDI-20391) always registers on `LogManager.getContext( false )`, so a truly separate context never gets the Kettle appender. |
| Does it matter at runtime? | **No.** In PDI 10.2 the shim classloader resolves to the same context. Kitchen runs `05` / `06` show the counters in the Kettle log and in `pdi.log`. Every execution runs on its own thread (`AbstractJobEntry:144`). |
| Is it a backport artifact? | **No.** `AbstractSqoopJobEntry.java` differs from master only in the license header. `AbstractSqoopJobEntryTest.java` differs only in the Mockito 1 imports. |
| Size of a fix | Test-only for the shared-context variant (a threaded test like the probe). The distinct-context variant also needs the pentaho-platform `LogUtil` change described in `SP-7670.md` 7.2. Either way it goes to **master first**. |

### 7.2 L248 `AbstractSqoopJobEntry.restoreSystemError()`: nested same-thread attach clears the thread-local logger

[Review comment r4376941344](https://github.com/pentaho/big-data-plugin/pull/3035#discussion_r4376941344) on
`CURRENT_SQOOP_LOGGER.remove();`:

> Detaching an inner entry clears the logger for a still-active outer entry on the same thread. After attaching
> A, attaching B, and removing B, subsequent stderr writes bypass A's Kettle log even though its log channel is
> restored and the shared proxy remains installed. Save and restore the previous thread-local logger on
> attachment and detachment, and add a regression assertion for a write after B finishes.

This is the same comment as `SP-7670.md` 7.1 (PR #3032, r4352328747), re-checked on the 10.2 code.

**Findings**

| Question | Answer |
|---|---|
| Is the described behaviour real? | **Yes, as stated.** A attaches on thread T, B attaches on T (overwrites `CURRENT_SQOOP_LOGGER`), B detaches (`remove()`). The proxy stays installed, but the supplier returns `null`, so A's later stderr output on T goes to the original `System.err`. `HadoopExecutionLogging.close()` restores the previous `logChannelId`, so the two mechanisms are inconsistent. |
| Can it happen at runtime? | **No.** On 10.2, `AbstractJobEntry.execute()` (`kettle-plugins/common/job/.../AbstractJobEntry.java:144`) runs every execution on a **new** `Thread`. `executeSqoop()` attaches at `AbstractSqoopJobEntry.java:365` and detaches in `finally` at `:374`. The only other production caller is the uncaught-exception handler (`:297`), which runs on the same thread. Master has the same callers. Per thread: one attach, one detach, never nested. |
| Is it a backport artifact? | **No.** `AbstractSqoopJobEntry.java` differs from master only in the license header. |
| Size of a fix | Small: save the previous thread-local logger on attach and restore it on detach (`remove()` only if it was `null`), plus a test that writes after the inner entry detaches. It would go to **master first**. |

**Options**

1. **Reply and resolve without a code change (recommended).**
2. **Master first, then backport.** Follow-up on master (save/restore + regression test), then backport to
   `SP-7670` and `SP-7669`.
3. **Change only the backport.** **Not recommended:** 10.2/11.0 would differ from master.

Suggested reply (**identical** to the reply posted on PR #3032, [r4352478253](https://github.com/pentaho/big-data-plugin/pull/3032#discussion_r4352478253)):

> Valid for nested attachment on the same thread, but production never nests: AbstractJobEntry runs each execution on a new thread, and executeSqoop() attaches/detaches once around runSqoop(). The code is an exact backport of master (pentaho/big-data-plugin#3012); any hardening should go to master first and then be backported.

### 7.3 L187 `AbstractSqoopJobEntryTest.attachesLoggingAppendersToShimLoggerContext`: the test loader shares the default context

[Review comment r4376941390](https://github.com/pentaho/big-data-plugin/pull/3035#discussion_r4376941390):

> This loader has the test classloader as its parent, so Log4j's classloader context selector can reuse the
> parent's existing `LoggerContext`. The assertion can therefore pass even if appenders are still attached only
> to the default context, leaving the main shim-context fix untested. Use a parent-less loader and assert that
> its context differs from the default, as the stderr-routing test already does.

This is the same comment as `SP-7670.md` 7.2 (PR #3032, r4352328822), re-checked on the 10.2 code.

**Findings**

| Question | Answer |
|---|---|
| Is the observation right? | **Yes.** `new URLClassLoader( new URL[ 0 ], getClass().getClassLoader() )` resolves to the **default** `LoggerContext` through the parent chain, so the test does not prove registration in a separate context. |
| Would the suggested test pass? | **No. Verified 2026-10-26** on `SP-7669` @ `2f8c171fcc` with a throwaway copy of the test, deleted afterwards. It used a parentless loader (`new URLClassLoader( new URL[ 0 ], null )`) and `assertNotSame( LogManager.getContext( false ), shimLoggerContext )`. `assertNotSame` passes, then the Kettle-appender check **fails** (`AssertionError`). This is consistent with the 7.1 probe, where distinct contexts deliver nothing. |
| Why does it fail? | `HadoopExecutionLogging` resolves the `Logger` from the shim loader's context, but registers the appender with `LogUtil.addAppenderWithLevel(...)` (pentaho-platform, PDI-20391). That method always uses `LogManager.getContext( false )`. |
| Does it matter at runtime? | **No.** In PDI 10.2 the shim classloader resolves to the same context. Kitchen runs `05` / `06` show the counters in the Kettle log and `pdi.log`. |
| Is it a backport artifact? | **No.** The test differs from master only in the Mockito 1 imports. `HadoopExecutionLogging` is identical to master, and `LogUtil` comes from PDI-20391 (master and SP-7690). |
| Size of a fix | **Not test-only.** It needs `LogUtil.addAppenderWithLevel(...)` (or `HadoopExecutionLogging`) to register on the logger's own `LoggerContext`. That is a pentaho-platform change, so it goes to **master first**, then gets backported (pentaho-platform + big-data-plugin) to 11.0 and 10.2. |

**Options**

1. **Reply and resolve without a code change (recommended).**
2. **Master first, then backport.** Follow-up ticket on master (pentaho-platform `LogUtil` + parentless-loader
   test), then backport to 11.0 and 10.2.
3. **Change only the backport.** **Not recommended:** a multi-repo divergence from master that goes beyond
   PDI-20034.

Suggested reply (**identical** to the reply posted on PR #3032, [r4352476220](https://github.com/pentaho/big-data-plugin/pull/3032#discussion_r4352476220)):

> Agreed that a parent-delegating loader shares the default LoggerContext. I checked: with a parentless loader the assertion fails, on master as well, because LogUtil.addAppenderWithLevel (pentaho-platform, PDI-20391) always registers in LogManager.getContext(false). In PDI the shim classloader delegates to PDI's loader, so it uses that same context and the counters reach the Kettle log (verified end to end). This PR is an exact backport of pentaho/big-data-plugin#3012. Supporting isolated shim contexts would be a master-level change in pentaho-platform LogUtil and will be raised as a follow-up rather than diverging here.
