The Sqoop job entry runs Sqoop **in-process**. When Sqoop submits its MapReduce job,
`org.apache.hadoop.mapreduce.Job` logs the job progress and the final `Counters: N` block (*File System
Counters*, *Job Counters*, *Map-Reduce Framework*, ...) through **slf4j**. On 11.0 those lines either
vanish or show only on the terminal. They never reach the Kettle log channel (Spoon *Logging* tab,
Kitchen `-logfile`, `logs/pdi.log`).

### 2.2 Host names without sudo

`setup.md` asks for `127.0.0.1 hadoop-hostname postgres-hostname` in `/etc/hosts`. That needs sudo.
`HOSTALIASES` (`~/.hosts.aliases`) is **not** a replacement. It is a glibc resolver feature that macOS
and the JVM ignore, and it only maps a name to another *name*, not to an IP address.

Use the JDK's own hosts file, scoped to the PDI JVM only. The mappers run inside Docker and resolve the
names through the compose network aliases, so they need nothing extra.

```bash
# ~/pentaho/tickets/PDI-20034/SP-7670/jvm-hosts
127.0.0.1 localhost <hostname> <hostname>.local hadoop-hostname postgres-hostname
::1 localhost
```

Passed with `PENTAHO_DI_JAVA_OPTIONS="... -Djdk.net.hosts.file=<path>/jvm-hosts"`. With this property
**every** lookup is served from the file, so it must also contain `localhost` and the machine host name
(`hostname`). Otherwise `InetAddress.getLocalHost()` fails inside Hadoop.

## 3. How to reproduce (AI compatible)

Everything is scripted. Runs are non-interactive (Kitchen) and each run leaves its evidence in
`~/pentaho/tickets/PDI-20034/SP-7670/evidence/<label>/` (`stdout.txt` = terminal, `kettle.log` = Kettle
log channel via `-logfile`, `pdi.log` = copy of `$PDI/logs/pdi.log`, `exit.txt`).

```bash
# ~/pentaho/tickets/PDI-20034/SP-7670/run_kitchen.sh <label>
unset PENTAHO_JAVA_HOME
export JAVA_HOME=$HOME/Library/Java/JavaVirtualMachines/corretto-17.0.14.7.1/Contents/Home

rm -f "$PDI/logs/pdi.log"
cd "$PDI" && ./kitchen.sh -file="$JOB" -level=Basic -logfile="$OUT/kettle.log" > "$OUT/stdout.txt" 2>&1
cp "$PDI/logs/pdi.log" "$OUT/pdi.log"
```

Check a run:

```bash
for f in stdout.txt kettle.log pdi.log; do
  echo "$f: $(grep -c 'Counters' evidence/<label>/$f) Counters lines, $(grep -c 'NOP' evidence/<label>/$f) slf4j NOP"
done
grep 'result=' evidence/<label>/kettle.log
```

Notes for an agent:

* `_PENTAHO_JAVA_HOME=` at the top of `stdout.txt` shows which JDK ran.
* In `stdout.txt`, lines that start with `HH:mm:ss,SSS LEVEL [Class]` come from the Log4j
  `PENTAHOCONSOLE` appender (terminal only). Lines that start with `yyyy-MM-dd HH:mm:ss.SSS - <entry> -`
  come from the Kettle log channel. Only the second kind proves the fix.
* No Spoon/GUI step and no job edits are needed.

## 4. Problems

Running the job on stock 11.0 exposes **three** independent defects. All three must be fixed before
the counters reach the Kettle log.

### P1 - Sqoop does not even start: `commons-cli` 1.2 in the plugin `lib/`

```
Sqoop import - ERROR ... java.lang.NoSuchMethodError: 'org.apache.commons.cli.Option$Builder org.apache.commons.cli.Option.builder(java.lang.String)'
    at org.apache.hadoop.util.GenericOptionsParser.buildGeneralOptions(GenericOptionsParser.java:234)
    ...
    at org.apache.sqoop.Sqoop.runTool(Sqoop.java:234)
```

`classpath.properties` (`classpath=./hadoop-configurations/apachevanilla`) puts the shim on the Kettle
plugin classpath. The plugin's own `lib/commons-cli-1.2.jar` is found first, ahead of the shim's
`commons-cli-1.5.0.jar`. Hadoop 3.4's `GenericOptionsParser` needs `Option.builder` (commons-cli ≥ 1.3).
The 1.2 jar reaches `lib/` through
`assemblies/pentaho-big-data-plugin/src/main/assembly/descriptors/plugin.xml` (`<include>commons-cli:commons-cli</include>`)
and is resolved transitively from the `pmr-libraries` zip dependency:

```
pentaho:pentaho-big-data-plugin:pom:11.0.0.0-SNAPSHOT
\- pentaho:pentaho-big-data-assemblies-pmr-libraries:zip:plugin:11.0.0.0-SNAPSHOT:compile
   \- commons-cli:commons-cli:jar:1.2:compile
```

The bump is required. Control run `07` (every other fix in place, only `lib/commons-cli-1.2.jar` put back)
fails with the same `NoSuchMethodError`. The official 11.0 `apachevanilla` plugin zip also ships
`lib/commons-cli-1.2.jar`, so Sqoop with that shim is broken on 11.0 regardless of logging. No plugin
source uses `org.apache.commons.cli` directly. The jar is only on the plugin classpath, where it shadows
the shim's 1.5.0 copy. 1.5.0 keeps the 1.2 API (`OptionBuilder`, `GnuParser`, ... deprecated but
present). The same bump also changes the `commons-cli` jar inside `pentaho-mapreduce-libraries.zip`
(`assemblies/pmr-libraries/src/main/descriptors/assembly.xml`), exactly as on master.

### P2 - Hadoop slf4j logging is discarded: slf4j 1.7 inside the shim `jetty-runner`

```
SLF4J: Failed to load class "org.slf4j.impl.StaticLoggerBinder".
SLF4J: Defaulting to no-operation (NOP) logger implementation
```

`hadoop-configurations/apachevanilla/lib/jetty-runner-9.4.57.v20241219.jar` is an uber jar that embeds
`org/slf4j/**` (slf4j-api **1.7.36**, 38 entries). That copy is picked up instead of PDI's
`slf4j-api-2.0.12` + `log4j-slf4j2-impl-2.25.5`. slf4j 1.7 finds no `StaticLoggerBinder`, so every
`org.slf4j.Logger` in Hadoop is a NOP. `org.apache.hadoop.mapreduce.Job` logs through slf4j, so the
progress and the counters are lost everywhere. Sqoop itself uses commons-logging, which is not affected.

The shim's `pom.xml` (`unpack-jetty-runner-jar` + `repack-jetty-runner-jar`) already builds
`target/extra-resources/jetty-runner-<v>.jar` **without** `org/slf4j/**`. The 11.0 assembly
(`shims/apachevanilla/driver/src/main/assembly/zip.xml`) still ships the original Maven artifact
instead.

### P3 - The Kettle appender only listens to `org.apache.sqoop`

On 11.0, `AbstractSqoopJobEntry.attachLoggingAppenders()` adds its `KettleLogChannelAppender` (filtered by
`SqoopLog4jFilter` on the `logChannelId` ThreadContext key) to `LOGS_TO_MONITOR[0]` = `org.apache.sqoop`
**only**. `LOGS_TO_MONITOR` also declares `org.apache.hadoop` and
`com.pentaho.big.data.bundles.impl.shim.sqoop.knox`, but they are ignored. With P1 + P2 fixed, the
`org.apache.hadoop.mapreduce.Job` events reach Log4j but go only to the `PENTAHOCONSOLE` appender
(terminal), which is the exact symptom of PDI-20034:

```
19:20:16,664 INFO  [Job] Counters: 33              <- terminal only
	File System Counters
	...
```

On master this attachment is done by `HadoopExecutionLogging.start( log, loggerClassLoader, LOGS_TO_MONITOR )`
(`org.pentaho.big.data.kettle.plugins.logging.HadoopExecutionLogging`). That class was added by
**PDI-20391** (`afb270241a`, *route Hadoop logs to the owning Kettle execution*), which is **not** in 11.0.
That is why the master PR does not apply cleanly.

### 5.1 `pentaho-hadoop-shims` (branch `SP-7670`)

`SP-7670`. It was not created in this session.

### 5.2 `big-data-plugin` (branch `SP-7670`): original commits on top of PDI-20391 (final content; now one squashed commit on SP-7691, see the status block)

The two original PDI-20034 commits (`8a8cf0378e`, `0c85f646e0`) are cherry-picked unchanged on top of
the PDI-20391 placeholders (see the status block at the top). Compared with master, the Sqoop and
logging files (`AbstractSqoopJobEntry`, `LoggingProxy`, `AbstractSqoopJobEntryTest`,
`HadoopExecutionLogging` + test, `dev-doc/hadoop-execution-logging.md`) differ only in the 11.0 license
headers. Each problem maps to:

* **P1**: `assemblies/pmr-libraries/pom.xml` commons-cli 1.2 → 1.5.0 (identical to master).
* **P3**: `HadoopExecutionLogging.start( log, loggerClassLoader, LOGS_TO_MONITOR )` attaches a
  channel-filtered Kettle appender to `org.apache.sqoop`, `org.apache.hadoop` and the Knox logger. The
  attach is called just before `runSqoop` with `hadoopClientServices.getClass().getClassLoader()`. The
  JVM-wide `System.err` proxy resolves its target logger per thread (`CURRENT_SQOOP_LOGGER`,
  `LoggingProxy( stream, Supplier<Logger>, level )`).
* **P2** is in `pentaho-hadoop-shims` (5.1).

Side effect of PDI-20391, visible in the runs: the Hadoop and Sqoop loggers become non-additive while the
execution appender is attached (`LogUtil.addAppenderWithLevel`). The terminal therefore shows only the
Kettle channel lines, not an extra raw `HH:mm:ss,SSS INFO [Job] ...` copy.

The two skipped files are not just missing context. They cannot be added on 11.0 without backporting
PDI-20391 itself:

* `HadoopExecutionLogging` uses `LogUtil.addAppenderWithLevel(...)` / `LogUtil.AppenderRegistration`,
  which only exist on `pentaho-platform` master (PR #6293, PDI-20391). They are absent from
  `pentaho-platform` `upstream/11.0` and from `lib/pentaho-platform-api-11.0.0.4-319.jar`, so adding the
  class would need a third repository.
* PDI-20391 also changes the MapReduce, PMR, Pig and Oozie job entries. Adding only the class for Sqoop
  would be a partial PDI-20391 backport hidden inside SP-7670.
* The paragraph PDI-20034 adds to `dev-doc/hadoop-execution-logging.md` describes the JVM-wide,
  reference-counted `System.err` proxy with a `ThreadLocal` target. That design is not on 11.0, so the
  text would be wrong there.

If parity with master is wanted, the clean route is a separate SP that backports PDI-20391 to 11.0
(big-data-plugin `afb270241a` + `5c2ab82684`, plus the pentaho-platform `LogUtil` change). After that,
PDI-20034 cherry-picks almost verbatim.

Resulting core change (11.0):

```java
public void attachLoggingAppenders() {
  attachLoggingAppenders( null );
}

void attachLoggingAppenders( ClassLoader loggerClassLoader ) {
  sqoopToKettleAppender = new KettleLogChannelAppender( log, new Log4jKettleLayout( StandardCharsets.UTF_8, true ) );
  Filter filter = new SqoopLog4jFilter( log.getLogChannelId() );
  ThreadContext.put( "logChannelId", log.getLogChannelId() );
  LoggerContext loggerContext = loggerClassLoader == null
    ? ( LoggerContext ) LogManager.getContext( false )
    : ( LoggerContext ) LogManager.getContext( loggerClassLoader, false );
  // Redirect all stderr logging to the first log to monitor so it shows up in the Kettle LogChannel
  Logger sqoopLogger = loggerContext.getLogger( LOGS_TO_MONITOR[ 0 ] );
  if ( sqoopLogger != null ) {
    stdErrProxy = new LoggingProxy( System.err, sqoopLogger, Level.INFO );
    System.setErr( stdErrProxy );
  }
  for ( String loggerName : LOGS_TO_MONITOR ) {
    LogUtil.addAppender( sqoopToKettleAppender, loggerContext.getLogger( loggerName ), Level.INFO, filter );
  }
}
```

Design notes:

* The PDI runtime uses Log4j's default `ClassLoaderContextSelector`. A shim classloader whose parent chain
  reaches PDI's loader gets the **same** `LoggerContext` (parent walk). The shim-classloader lookup copied
  from master is therefore a no-op on this runtime. It is kept for parity with master and for isolated
  (parent-less) loaders, which `redirectsSystemErrorToTheLoggerOfTheOwningExecution` covers.
* `LogUtil.addAppender` / `removeAppender` (`org.pentaho.platform.api.util.LogUtil`, 11.0) always work on
  `LogManager.getContext( false )`. Master's `LogUtil.addAppenderWithLevel` does the same, so behaviour
  is equivalent.
* Moving the attach call to just before `runSqoop` matches master. Errors before that point are still
  logged with `logError`. `removeLoggingAppenders()` in `finally` is null-safe when nothing was attached.

### 7.1 L248 `AbstractSqoopJobEntry.restoreSystemError()`: nested same-thread attach clears the thread-local logger

[Review comment r4352328747](https://github.com/pentaho/big-data-plugin/pull/3032#discussion_r4352328747) on
`CURRENT_SQOOP_LOGGER.remove();`:

> When two entries attach on the same thread, as in the new routing test, the second attachment replaces the
> first entry's thread-local logger. Detaching the second entry then clears the logger even though the first
> entry and the shared proxy remain active. `HadoopExecutionLogging.close()` restores the first entry's
> log-channel ID, but subsequent `System.err` writes fall back to the original stream instead of reaching that
> entry's Kettle log. Preserve and restore the previous logger for nested scopes, or track active targets per
> thread. Extend the routing test to verify a write after the inner entry detaches.

**Findings**

| Question | Answer |
|---|---|
| Is the described behaviour real? | **Yes, as stated.** Entry A attaches on thread T (`CURRENT_SQOOP_LOGGER` = A's logger), entry B attaches on the same thread T (overwrites it with B's logger), B detaches (`remove()`). The shared proxy stays installed (`systemErrorRedirectorCount` = 1), but `LoggingProxy` gets `null` from the supplier and writes to the original `System.err`. A's later stderr output on T is no longer routed to A's Kettle log. `HadoopExecutionLogging.close()` does save and restore the previous `logChannelId` for nested scopes, so the two mechanisms are inconsistent. |
| Can it happen at runtime? | **No.** `AbstractJobEntry.execute()` (`kettle-plugins/common/job/.../AbstractJobEntry.java:144`) runs every execution on a **new** `Thread( getExecutionRunnable( jobResult ) )`. `executeSqoop()` attaches just before `runSqoop()` and calls `removeLoggingAppenders()` in `finally`. The uncaught-exception path (`handleUncaughtThreadException`) runs on that same dying thread. No other production code calls `attachLoggingAppenders()` / `removeLoggingAppenders()`. Per thread there is therefore exactly one attach followed by one detach, and never nesting. Only the unit test `redirectsSystemErrorToTheLoggerOfTheOwningExecution` attaches two entries on one thread, and it only writes while both are attached. |
| Is it a backport artifact? | **No.** `restoreSystemError()` in `388fbaabdd` is identical to master (PR #3012, merge `2f224dd256`), and master has not changed `AbstractSqoopJobEntry.java` since. |
| Size of a fix | Small. Keep the previous thread-local value in an instance field when attaching (`previousSqoopLogger = CURRENT_SQOOP_LOGGER.get()` before `set`). When detaching, restore it (`set( previous )`, or `remove()` if it was `null`) instead of always calling `remove()`. Extend the test with a `System.err` write after the inner entry detaches, asserting it reaches the outer entry's logger. This assumes LIFO detach on the thread, which matches `HadoopExecutionLogging`. |

**Options**

1. **Reply and resolve without a code change (recommended).** The scenario is unreachable in production
   (fresh thread per execution, paired attach/detach), and the code is identical to master PR #3012, so the
   backport keeps parity. Suggested reply: *"Valid for nested attachment on the same thread, but production
   never nests: `AbstractJobEntry` runs each execution on a new thread, and `executeSqoop()` attaches/detaches
   once around `runSqoop()`. The code is an exact backport of master (pentaho/big-data-plugin#3012); any
   hardening should go to master first and then be backported."*
2. **Fix on master first, then backport.** Open a follow-up ticket/PR on master (save/restore the previous
   logger + extended test), then cherry-pick it into `SP-7670` (11.0) and `SP-7669` (10.2). This keeps parity,
   but SP-7670 waits for the master change, or the fix is backported later as a separate change.
3. **Fix only in the backport.** Apply the fix to `SP-7670`, and mirror it in `SP-7669`. This resolves the
   comment immediately, but 11.0/10.2 then differ from master. That goes against the "minimal changes
   compared to the original commits" rule of this backport, and future master changes to this method would
   conflict.

### 7.2 L189 `AbstractSqoopJobEntryTest.attachesLoggingAppendersToShimLoggerContext`: the test loader shares the default context

[Review comment r4352328822](https://github.com/pentaho/big-data-plugin/pull/3032#discussion_r4352328822):

> This loader has the test classloader as its parent, allowing Log4j's ClassLoaderContextSelector to reuse the
> parent's LoggerContext. The assertion can therefore pass even if HadoopExecutionLogging ignores the supplied
> loader and attaches only to the default context. [...] Use a parentless loader and assert that its context
> differs from the default before checking the Kettle appender.

**Findings**

| Question | Answer |
|---|---|
| Is the observation right? | **Yes.** `ClassLoaderContextSelector` walks the parent chain, so `new URLClassLoader( new URL[ 0 ], getClass().getClassLoader() )` resolves to the **default** `LoggerContext`. The assertion would pass even if the supplied loader were ignored, so the test does not prove cross-context registration. This matches the design notes in 5.3. |
| Would the suggested test pass? | **No, verified 2026-10-22.** A throwaway copy of the test with a parentless loader (`new URLClassLoader( new URL[ 0 ], null )`, then `assertNotSame( LogManager.getContext( false ), shimLoggerContext )`, then the Kettle-appender check) **fails** on `SP-7670` @ `388fbaabdd` with `AssertionError` at the appender check. The probe test was deleted afterwards. |
| Why does it fail? | `HadoopExecutionLogging` resolves the `Logger` from the shim loader's context, but registers the appender with `LogUtil.addAppenderWithLevel(...)` (pentaho-platform, PDI-20391). That method always works on `LogManager.getContext( false )`, i.e. the **default** context. A truly separate shim context never gets the Kettle appender. |
| Does it matter at runtime? | **No.** In PDI the shim classloader (`HadoopConfigurationClassLoader`, or the plugin classloader through `classpath.properties`) has PDI's loader in its parent chain, so its context *is* the default one. That is why runs `13` / `14` show the counters in the Kettle log. The gap only matters for a shim loader without that parent chain, which PDI 11.0 does not use. |
| Is it a backport artifact? | **No.** The test and `HadoopExecutionLogging` are identical to master (PR #3012), and `LogUtil` comes from PDI-20391 (master and SP-7691). |
| Size of a fix | **Not test-only.** Making the stronger test pass requires `LogUtil.addAppenderWithLevel(...)` (or `HadoopExecutionLogging`) to register on the logger's own `LoggerContext`, which is a pentaho-platform change. The alternative is to drop the claim that a separate shim context is supported. Either way it is a master-level design decision (PDI-20391 / PDI-20034 follow-up), followed by backports to 11.0 (pentaho-platform + big-data-plugin) and 10.2. |

**Options**

1. **Reply and resolve without a code change (recommended).** The weaker test reflects how PDI actually
   wires the shim classloader (same context through the parent chain). The stronger test would fail against
   master as well, and the code is an exact backport of master. Suggested reply: *"Agreed that a
   parent-delegating loader shares the default LoggerContext. I checked: with a parentless loader the
   assertion fails, on master as well, because `LogUtil.addAppenderWithLevel` (pentaho-platform, PDI-20391)
   always registers in `LogManager.getContext(false)`. In PDI the shim classloader delegates to PDI's loader,
   so it uses that same context and the counters reach the Kettle log (verified end to end). This PR is an
   exact backport of pentaho/big-data-plugin#3012. Supporting isolated shim contexts would be a master-level
   change in pentaho-platform `LogUtil` and will be raised as a follow-up rather than diverging here."*
2. **Fix on master first, then backport.** Open a follow-up ticket for master: register the appender on
   the logger's own `LoggerContext` (pentaho-platform `LogUtil` and/or `HadoopExecutionLogging`), then switch
   the test to a parentless loader with `assertNotSame( default, shimContext )`. Backport that to 11.0 and
   10.2 afterwards (pentaho-platform + big-data-plugin). This keeps parity, but needs a pentaho-platform
   change and a coordinated release.
3. **Change it only in the backport.** Either (a) strengthen the test as suggested and also change the
   registration in the 11.0 `LogUtil` / `HadoopExecutionLogging`, which is a multi-repo divergence from
   master, or (b) keep the code and only make the test's intent explicit (e.g. rename it or add a comment
   saying it covers a parent-delegating shim loader), which is a test-only divergence. Both make 11.0 differ
   from master. Option (a) also widens the backport beyond PDI-20034 and goes against the "minimal changes
   compared to the original commits" rule.

Pitfalls:

* **Reusing the HDFS volume across Hadoop versions breaks the NameNode.** A 3.3.6 image under 3.4.1 fails
  with `File system image contains an old layout version -66`, and the container stays at
  `health: starting`. Always use `down -v`.
* **The snapshot apachevanilla `lib/` silently loses the counters.** Its `jetty-runner` bundles slf4j 1.7,
  so you get `SLF4J: Defaulting to no-operation (NOP) logger implementation` and 0 `Counters` lines, while
  the job still succeeds. See run `17`.
* **`pentahoNamedCluster` is required.** Selecting the cluster in the Sqoop step fails with PDI-20947, which
  is unrelated to this ticket.
